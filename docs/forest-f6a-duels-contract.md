# Forest friendly duel invitations: F6A contract

F6B.1 extends this contract; see [friendly combat handoff](forest-f6b-friendly-combat-contract.md) for READY, STARTED, cancellation and match routes.

All routes require the existing authenticated session and client build header. Enable `FOREST_DUELS_ENABLED=1` only on the active Forest lease owner, with Forest enabled. Otherwise the routes return `503 {"error":"FOREST_DUELS_UNAVAILABLE"}`. No Ranked flag or PvP secret is required for invitations.

* `GET /forest/duels/state` returns `{player_id, incoming: Invite[], outgoing: Invite[], accepted: Invite[]}` for the authenticated player. At most one record is returned across these lists. Pending records appear only in the appropriate incoming or outgoing list; accepted records appear in `accepted` for both participants. Names come from the server's player records.
* `POST /forest/duels/request` takes `{target_player_id, client_action_id}`. Both participants must have entered active sockets in the same authoritative room and be free of unexpired Ranked queue entries and active PvP matches.
* `POST /forest/duels/respond` takes `{invite_id, accept: boolean, client_action_id}`. Only the recipient can decide. Acceptance rechecks both active sockets are in the original room and both players are free of Ranked activity.
* `POST /forest/duels/cancel` takes `{invite_id, client_action_id}`. Only the challenger can cancel a pending invitation; either participant can cancel an accepted reservation.

Successful mutations return `{invite: Invite}`. An `Invite` contains `invite_id`, `challenger_id`, `challenger_name`, `recipient_id`, `recipient_name`, `originating_zone`, `status`, `created_at`, `updated_at`, and `expires_at`. Times are Unix milliseconds. The stable `invite_id` identifies popup and preparation state; never infer identity or room from client data.

Pending invitations expire after 45 seconds. Acceptance changes `PENDING` to `ACCEPTED` and starts a 180-second preparation reservation, which survives socket suspension or leaving Forest. On the first subsequent operation at or after the deadline, expiry changes the status to `EXPIRED` and releases both participant reservations atomically. Decline and cancellation release both immediately. Expired or cancelled records cannot be accepted. F6B.1 adds the server-side `STARTED` transition when both participants are ready.

Use a unique `client_action_id` for each user action. Repeat the exact same body and ID after an uncertain response. The server replays the original status and body for seven days; conflicting reuse within that period returns `409 ACTION_CONFLICT`. History is capped at 500 actions per player within the retention period, and invitations have sender and recipient rate limits. After retention expires an ID is no longer protected against reuse, so clients must continue using globally unique IDs.

Errors include `400 INVALID_REQUEST`, `INVALID_TARGET`, `INVALID_ACTION_ID` or `SELF_DUEL`; `404 PLAYER_UNAVAILABLE` or `INVITE_UNAVAILABLE`; `409 FOREST_ROOM_MISMATCH`, `PLAYER_BUSY`, `INVITE_NOT_PENDING`, `INVITE_NOT_ACTIVE` or `ACTION_CONFLICT`; and `429 DUEL_RATE_LIMIT` or `ACTION_LIMIT`. Authentication, idle, update and rate-limit errors follow existing middleware. An unavailable lease owner or feature returns 503. Failures that reached the idempotent transaction are replayed too: a new attempt after a definitive failure needs a new action ID.

F6B must introduce an explicit **friendly versus Ranked match kind** and enforce it in creation, recovery and settlement. Friendly matches must never update Mastery Points, ratings, leagues or leaderboards. Reuse the secure PvP RNG, catalogs, `trustedPvpSnapshot`, combat creation and match lifecycle with server-owned loadouts. Before atomically consuming an accepted reservation and creating a match, check expiry, both participants and their current Ranked queue/match state again. Ranked queue joins are not changed by F6A, so a player can join Ranked after an invitation is accepted; F6B must resolve this race transactionally before starting. A client must never create an authoritative match, provide a trusted snapshot, choose a winner, or extend a reservation.
