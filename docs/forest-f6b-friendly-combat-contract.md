# Friendly duels: F6B.1 client handoff

All routes use the existing authenticated session and client-build requirements. Forest duels and the active Forest lease must be available; Acceptance, READY and match routes also require a valid `PVP_RNG_SECRET` of at least 32 UTF-8 bytes. `PVP_ENABLED` controls Ranked routes only. Feature defaults remain disabled.

After an invitation is accepted, suspend Forest presence and open the existing loadout. Both participants choose their own setup. Socket presence is no longer required during preparation. The accepted invitation expires at its server-provided `expires_at`; READY never extends it.

* `POST /forest/duels/ready` takes `{invite_id, selection, client_action_id}`. `selection` has Ranked's `entity_id`, `weapon_ids`, `homunculus_id`, `spell_ids`, and `mode`. The server validates and freezes the caller's setup. A successful response is `{state:"WAITING", invite_id}` or `{state:"STARTED", match_id}`. Use a unique action ID; retry an uncertain request with exactly the same body and ID. A replay of the first READY can still return its original WAITING response after the match starts: poll state for the current answer. A different selection after ready returns `409 READY_CONFLICT`.
* `GET /forest/duels/state` keeps F6A's `{player_id,incoming,outgoing,accepted}` lists. Accepted entries also contain `ready:{player:boolean,enemy:boolean}`. When available, `started:{invite_id,match_id}` identifies the most recently started friendly duel for that participant, including after restart and after completion. Compare `invite_id` with the preparation being recovered; preserve the match ID locally when known.
* `GET /forest/duels/match/state?match_id=...&after=0&chat_after=0` returns the existing participant-specific PvP state, including `kind:"friendly"`, combat revision, deadline, score, fighters, readiness, events, chat, and `result`. A finished friendly result contains only `result` (`win`, `loss`, or `draw`); it has no MP, division, or season fields. The match ID can be omitted to locate the participant's most recent friendly match.
* `POST /forest/duels/match/decision` takes `{match_id,client_action_id,combat_revision,decision}`. `POST /forest/duels/match/forfeit` takes `{match_id,client_action_id}`. Both return the existing participant-specific PvP state. `POST /forest/duels/match/chat` takes `{match_id,client_message_id,text}` and returns `{message,duplicate}`. These use the same idempotency, turn deadlines, validation, and chat limits as Ranked. Each match endpoint requires both membership and friendly kind.

On restart, fetch duel state and compare the invitation ID. If accepted, inspect the ready flags and retry or continue polling; if started, recover the match ID and fetch match state. A participant may cancel an accepted preparation through `POST /forest/duels/cancel` with `{invite_id,client_action_id}`. Expired, declined, or cancelled invitations cannot start: discard the preparation and safely return to Forest. A started match cannot be cancelled through invitations; use its forfeit route. Availability, authorization, invalid setup, busy, stale revision, and rate-limit errors follow the corresponding existing routes.
