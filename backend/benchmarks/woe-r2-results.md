# WOE and Core Defense R2 local measurements

2026-11-25, local Windows, Bun 1.3.8 and Godot 4.6. These are isolated test services and temporary SQLite databases, not production or VPS measurements. The production flags remain off by default. The authenticated HTTP probe starts a real API and Redis, uses file-backed SQLite WAL, `synchronous=FULL`, `busy_timeout=5000`, and the default 1,000-page auto-checkpoint. It injects 30 synthetic units per match near the plaza, then uses real HTTP polling, deployments, events and the actual timer. WOE opponents are NPCs; a finished match may be replaced using fixture-side database services. Pulse profiling is enabled for the probe and writes a timing line per pulse. PostgreSQL is deliberately unavailable in this fixture; account validation uses a 100 ms fallback timeout, so the measured HTTP latency is not representative of healthy production authentication.

Two authenticated Godot clients played a human 1v1 with no other test workload. At tick 1800, the pre-change scheduler took **197,545 ms**; the monotonic scheduler took **179,924 ms**, and after tightening its exception guard a repeat took **179,963 ms**. All produced a timeout draw. These are individual runs, not a statistical confidence interval.

The before and after HTTP runs change both scheduler and poll rate, so they do not isolate the room-write change. Terminal-match polling also includes up to one poll interval after the last tick, reducing the reported rate for those segments. In the four-session replacement run, observed wall time minus simulated time ranged from approximately **−53 to +176 ms** across the individual match segments; the gap between the completed WOE segment's last poll and its replacement's first poll was 1.15 s. It recorded 1,628 retained events and 4.14 MB WAL before a passive checkpoint; it reported `busy=0`, 35 frames and 35 checkpointed. Server CPU was 4.63 seconds over 65.7 seconds; sampled RSS was 204.3 MB at start and 203.5 MB at end. The eight-session run recorded 3,427 events, 4.16 MB WAL and a passive checkpoint of 707/707 frames with `busy=0`; CPU was 12.55 seconds over 65.7 seconds, and sampled RSS was 209.9 MB at start and 122.4 MB at end. RSS values are endpoints, not peaks. Automatic checkpoints reuse the WAL, so its file size is not cumulative write volume. Two eight-session deployment attempts received 409 responses; no 429 or 5xx responses occurred.

The separate `woe_persistence_benchmark.ts` compares the base commit's service against the modified service on identical cloned four-match databases. It deliberately disables automatic checkpointing to count cumulative WAL bytes; it is not a production-equivalent load test. Three 100-pulse runs each wrote 16,286,392 bytes before and 10,670,832 bytes after. Median-of-three pulse p50 was 9.04 ms before and 8.06 ms after; median-of-three p95 was 10.88 ms before and 10.78 ms after. All final passive checkpoints reported no busy frames. The change removes the duplicate room snapshot write; STARTED lobby views now read the same committed `woe_matches.state_json` as match state.

The new scheduler uses monotonic deadlines, runs at most three catch-up pulses in one callback, and caps outstanding wall-time debt at 300 ms. Under greater overload it allows simulation to lag rather than skipping game ticks or accumulating unbounded debt. Individual match failures have exponential retry delays capped at 30 seconds; a scheduler-level exception delays the next attempt by one second. Loss of the Forest lease retains the existing fencing policy, which intentionally terminates the API process for supervisor restart.

The post-change HTTP runs preceded a final change that moved the scheduling-availability check inside the existing exception guard. That change leaves the normal scheduling path unchanged; the final 179,963 ms isolated timeout and focused exception tests ran after it.

Reproduce from `backend` with `R2_MATCHES=4 R2_SECONDS=65 R2_POLL_MS=1000 R2_REPLENISH=1 bun run src/tests/woe_http_load.ts` and `bun run src/tests/woe_persistence_benchmark.ts`; use PowerShell environment-variable syntax on Windows. Temporary SQLite directories may remain if Windows retains a file handle; the scripts print their exact paths. These short synthetic runs support an initial **four shared matches** for controlled staging, subject to target-host monitoring. They do not establish public capacity or validate the target VPS.
